# IntoL — iPhone 向けイントロクイズ

SwiftUI 製 iOS 17+ アプリと、Coolify 用 Node.js サーバーです。`rule.md` をゲーム仕様の参考にし、個人学習と少人数のプライベート対戦向けに作成しました。画面はライト／ダーク両方に対応し、プレイでは人数を選び、ソロはモードとプレイリスト、対戦はルーム作成またはコード参加へ進みます。選択画面は説明付きのカードを使い、横方向の共有軸で遷移します。下部の「プレイ」を押すと最初のロゴ画面に戻ります。

## できること

| モード | 音源 | 条件 |
| --- | --- | --- |
| ひとりで（イントロ） | Apple Music のプレイリスト | 再生には本人のサブスクリプションが必要 |
| みんなで | ホストの Apple Music のプレイリスト | 最大4人、全員が Apple Music の再生条件を満たす必要があります |
| サビトロ | Apple Music のプレイリストを iTunes の試聴音源と照合 | ひとりでも最大4人でも遊べます。ライブラリアクセスとサーバー設定が必要 |

通常のプレイ画面の導線は以下の通りです。

- ひとりで → イントロ／サビトロ → プレイリスト選択 → プレイ
- ひとりで → ランク測定 → 共通曲集で15〜20問（Apple Music、ベータ版）
- みんなで → ルームを作る → イントロ／サビトロ → ホスト待機室
- みんなで → コードで参加 → 6文字コード入力 → 参加者待機室

ランク測定は716曲の共通曲集から回答に応じて出題し、F・E・D・C・C+・B・B+・A・A+・S・S+の11段階で推定ランク・測定幅・最高記録を表示します。難易度は試遊前の仮設定で、通常ソロのF〜S+とは別の評価です。ランク履歴20回と最高記録もCloudKitに同期します。過去の曲集を含む最高ランクの丸型バッジを、自分とフレンド・対戦相手のプロフィールに表示します。他の人への表示には更新済みサーバーが必要です。[仕様・曲集と検証方法](docs/rank-measurement.md)を参照してください。

入力画面のコードは6つのボックスに表示し、英字を自動で大文字にします。6文字が揃うと自動で参加を試み、エラー時には入力し直しと再試行ができます。クリップボードにテキストがあれば貼り付けボタンを表示し、「ルームコード: GKPZQY」のような招待文からコードを抽出します。待機室の表示用コードは等幅文字のチップにまとめ、「コピー」と「共有」を同じ形のボタンで並べています。「あなた」とホストのラベルを参加枠に表示し、満員のときは招待を無効にして理由を添えます。設定カードはプレイリスト・問題数・ライフの要約を表示し、詳細を開くとプレイリスト・ルール・ハンデを確認・変更できます。ホストの開始ボタンは2人以上、十分な曲数、Apple Musicの再生条件、準備済みルームでは全員の音源準備を条件にし、満たさないときは理由を表示します。開始処理中も条件を再確認し、最新アプリが作成するルームではサーバーも2人以上を要求します。旧クライアント・既存ルームのサーバー仕様は維持し、アプリ側はすべての待機室で2人以上を必要とします。参加者側には「ホストの開始を待っています…」の固定バーを表示します。

待機室と対戦中の×ボタンには、状況別の説明付きの退室確認を表示します。キャンセルが塗りボタン、退室する操作が赤い枠線ボタンです。ホストが退室すると残った参加者へ自動交代し、最後の1人が退室するとルームは閉じられます。ゲーム中の退室者は最終順位から外れますが、すでに保存された問題ごとの正誤記録は残ります。アカウント名は通常の文字色と隣接する編集アイコンで表示し、未接続状態には注意色を使います。フレンド情報は下に引いて更新でき、招待にはモードと現在の人数を表示します。人数情報とサーバー側の開始条件を反映するには、この変更を含む対戦サーバーを再デプロイしてください。

1曲30秒の PUSH、1文字5秒の4択、解答権、誤答・ライフ・得点、全員スキップ、最終順位、ソロの0〜100点と15段階ランクを実装しています。回答中は正解の文字数を表示しません。対戦サーバーが PUSH の到着順を判定します。ほぼ同時の PUSH で解答権を取れなかった場合もルームに残り、画面内に結果を通知します。対戦中のプレイヤー欄はPUSH前は得点順、誰かがPUSHした後はその曲のPUSH受付順に並び、順位・名前・得点・現在の問題の○×を表示します。未PUSHの人は後ろに得点順で並び、次の曲と最終結果では得点順に戻ります。順位ラベルは得点順位を示し、ライフはハート、SKIP投票はアバターのバッジで示します。大きな文字サイズでは2列に切り替わります。PUSH時刻は押した瞬間に本人のステータスへ表示し、通信後にサーバーの記録で更新します。ほかの参加者のPUSH時刻も状態通知を受けた時点で表示します。正誤が確定すると、アバター右上に正解は緑背景の白い○、不正解は赤背景の白い×を表示します。出題タイマーは0.01秒単位、PUSH時刻と平均PUSH時間は0.001秒単位で表示します。SKIPは、未回答者（失格者を除く）が全員投票すると成立します。正解者・誤答者の投票は成立条件に含めません。解答中のプレイヤーは未回答者に含みます。未投票者の退出時にも成立条件を再判定します。通常モードではSKIP成立でPUSH受付を終了し、進行中の解答がすべて終わってから正解を発表します。通常モードの解答権人数は1〜4人（初期値2人）で、空き枠があれば複数人が並行して解答できます。PUSHした本人の曲はすぐに止まり、正解者が出ても受付中はほかの人がPUSHできます。30秒経過、全枠使用、または回答可能な人がいなくなると受付を終了し、全員の出題曲を止めます。受付終了後も進行中の解答は各文字の5秒制限で続行し、すべて終わってから正解曲を再生します。複数正解時は正解者のPUSH受付順に順位を付けます。1st正解ボーナスは正解者の中で最初にPUSHしたプレイヤーに適用します。1st誤答ペナルティは従来どおり、その曲で最初にPUSHしたプレイヤーが誤答した場合にだけ適用します。エンドレスモードでは解答権人数に関係なく1人ずつ解答し、回答中は全員の曲と出題タイマーが止まります。1st正解ボーナスと1st誤答ペナルティは適用せず、設定欄を解答権人数と同じようにグレーアウトします。設定値は保持し、通常モードに戻すと再び適用します。僅差でPUSHした人は解答待ちになり、前の人が誤答または時間切れになるとPUSH順に解答できます。待機者がいなくなった誤答後は停止位置から曲を再開します。各ラウンドでは「第○曲目」と読み込み表示を挟み、対戦は全員の準備完了後に5秒のカウントダウンを始めます。端末は通信の往復時間からサーバー時計との差を推定して同じ開始時刻に合わせ、端末内に保存した音源は再生時刻を予約します。Apple Music は MusicKit が時刻指定再生を提供しないため、通信・バッファリング・音声出力の遅延まで完全に一致させることはできません。

復習リストは「覚えてない」「覚えた」を各50曲、ソロ履歴は直近5回です。統計、ジャンル別正答率、8種類の称号、切断後5分以内の復帰、ホスト自動・手動交代にも対応しています。名前・アイコン・復習・履歴・統計・称号・音量設定はCloudKitのPrivate Databaseに保存し、端末にもキャッシュします。同じiCloudアカウントの別端末へプロフィールを復元できます。CloudKit未設定・未サインイン・オフライン時も端末で利用できます。ルームとフレンド申請・招待は引き続きサーバーの `DATA_DIR` に保存します。既存の端末とサーバーの個人記録はCloudKitへ取り込みます。

対戦中も空きがあれば、6文字のコードまたはフレンド招待から途中参加できます。開始前の招待は対戦中も有効で、対戦画面の「フレンドと招待」から新しく招待することもできます。途中参加者は得点0・設定どおりの初期ライフで合流し、受付中の問題から解答できます。音源は読み込み完了時点の再生位置に合わせます。解答受付終了後や正解発表中に合流した場合は、次の問題を待ちます。満員のルームと終了したゲームへの新規参加はできません。途中参加を利用するには、アプリと対戦サーバーの両方を更新してください。

リザルトの「曲ごとの結果」は初期状態で閉じており、見出しを押すと開閉できます。ソロと対戦の両方で利用できます。プレイヤーの並び順は `sh scripts/test_room_player_ordering.sh` で確認できます。

参加者への設定共有と、対戦結果の曲ごとの正誤表示には、`lobby-config` と `roundSongs` に対応したこの版のサーバーが必要です。旧サーバーでも対戦できますが、待機中の設定共有と曲ごとの対戦結果は利用できません。

ホームと出題中の波形、回答のカーソル、得点・ランクの演出は「視差効果を減らす」に対応しています。選択肢の誤答は赤で約0.2秒表示し、正解時の緑色のフレームとチェックマークは表示しません。PUSH・回答・残り5秒には触覚フィードバックを付けています。結果画面から共有用の画像を生成できます。触覚とApple Musicの再生は実機で確認してください。

画面確認用の `UIExamples.swift` は Debug ビルドだけに含まれます。Xcode の Preview または起動引数 `--ui-preview=<scenario>` で確認できます。`<scenario>` に `home`、`mode`、`room-selection`、`code`、`friends`、`friends-request`、`friends-invite`、`account`、`lobby-host`、`lobby-empty`、`lobby-ready`、`lobby-ready-shortage`、`lobby-guest-dark`、`lobby-guest-large-text`、`answer`、`answer-large-text`、`reveal`、`result-dark`、`solo-result` を指定すると、音源の準備をせずに各画面を確認できます。

待機室の開始条件・退室説明・旧サーバーの招待データとの互換性は `sh scripts/test_room_lobby_readiness.sh`、サーバーの人数チェックと招待人数の更新は `cd server && npm test` で確認できます。

## CloudKitの設定

Apple Developer側の設定は別途必要です。[CloudKitの設定と動作確認](docs/cloudkit-setup.md)に、コンテナ作成、XcodeのiCloud設定、`.env` の `APP_CLOUDKIT_ENABLED=true`、初回同期、Productionへのスキーマ公開の手順をまとめています。現在のコンテナIDの既定値は `iCloud.com.intro.IntoL` です。CloudKit対応後も、対戦中の通信には既存のWebSocketを使います。

曲名の長音符「ー」と英字同士を直接つなぐハイフンは回答対象です。その他の記号は解答不要で、英字同士をつながない `-`、`(`、`feat` 以降も省略できます。対戦の最終順位は得点、同点なら残ライフで決め、失格者は最下位にします。リザルトの1〜3位は淡い金・銀・銅で表示します。ホストはルール未設定のルームを作り、待機画面でプレイリストとルールを選んで「ゲームを開始」を押します。その後、全員が音源を準備し、準備完了で自動的にカウントダウンへ進みます。終了後の「ルームに戻る」は同じ参加者と未出題曲の履歴を保ったまま、ルール未設定の待機画面に戻ります。次の対戦ではルールを変更しても未出題曲を優先します。同じルームのプレイヤーにフレンド申請を送り、承認するとフレンドになります。待機中のルームからフレンドを招待でき、受け取った人は「フレンド」タブから6文字のコードを入力せずに参加できます。

ルーム作成後、待機中のホストは「ハンデを設定」から参加プレイヤーごとに0〜30秒を指定できます。対象プレイヤーは各問題の再生開始から指定時間が過ぎるまでPUSHできず、残り時間が画面に表示されます。設定は開始後に変更できません。

### 対戦の通信方式

対戦中は認証付きの WebSocket 1本で PUSH・回答・準備完了などの操作と状態通知を送受信します。サーバーは到着順と制限時間を判定し、操作結果を同じ接続で返します。PUSH 直後は端末に判定中の状態を即座に表示し、相手の PUSH はサーバーからの通知で更新します。WebSocket に接続できない環境では従来の SSE 通知と HTTP 操作に切り替え、接続を約1分ごとに再試行します。SSE にも対応しない旧サーバーでは2秒間隔で状態を取得します。各端末に送る状態はその参加者の解答選択肢だけを含み、発表前の曲名は含みません。カウントダウン開始・30秒の受付終了・各文字の5秒制限もサーバー側のタイマーで通知します。

従来の0.5秒間隔の取得では、4人対戦が500ルーム同時に進むと最大約4,000件/秒の状態取得が発生し、相手の操作反映には最大約0.5秒かかります。WebSocket と SSE は合わせて最大2,000本の接続を維持し、15秒ごとに生存確認を行います。少人数対戦・単一サーバーの構成には妥当ですが、2,000人同時接続時のファイル記述子数、メモリ量、プロキシの WebSocket Upgrade 対応は実環境で確認してください。複数レプリカへ増やす場合は、ルーム状態と通知の共有基盤が必要です。ネットワークの往復時間や外部音楽サービスの再生開始時間は WebSocket だけでは短縮できません。

曲名に「~」「〜」「～」がある場合は、最初の記号とそれ以降を解答対象から外します。正解発表には元の曲名を表示します。

１文字目のダミーは音源元にかかわらず iTunes Search API で同一アーティストを検索し、上位６曲から正解曲を除いて異なる先頭文字をランダムに最大３つ選びます。足りない場合は同じ文字種の候補で補います。２文字目以降はプレイリストと同梱の曲名データから、同じ接頭辞を持つ別曲の次の文字、直前の文字に続く頻度が高い文字、正解と同じ文字種の候補の順に選びます。2015〜2026年の Billboard JAPAN チャートを基に約1,100曲の題名を追加し、ソロと対戦の両方で使います。小書き仮名と長音符はダミーに使いません。正解発表の再生は、利用可能なフル音源に対して「手動確認したサビDB→Songle→試聴音源の冒頭→音源の長さから推定した位置」の順に試します。サビDB・Songleの位置は1.5秒手前から再生します。DBは曲名とアーティストで照合し、アルバムや曲IDが変わっても同じ位置を使います。サビトロはフル音源を持たないため、試聴音源の冒頭から再生します。フル曲のサビ時刻を試聴音源に適用しません。推定位置は曲長の32%を30〜90秒に収めた値の1.5秒手前とし、短い音源では少なくとも末尾5秒を残します。再生に失敗した場合も次の候補へ進みます。曲名コーパスは選択肢用であり、追加した曲の音源を同梱するものではありません。

各問題の開始前には、端末でその曲の音源を準備します。共有 WAV と試聴音源は端末の一時領域へ読み込みます。Apple Music 音源は MusicKit が再生します。Apple Music には全出題曲の音声をアプリ側へ事前取得する API がないため、曲情報と再生可能性を確認しながら進行します。

プレイリストからの出題曲の照合は最大6曲を並行して行い、必要な数の未出題曲がそろった時点で終了します。照合済みの曲はアプリ起動中に再利用し、開始操作の通信に失敗した場合も準備済みの出題曲を保持して再試行します。すでに出題曲が確定した待機ルームでは、プレイリストを照合し直さずに開始します。並行処理・途中終了・キャッシュ・再試行の回帰テストは `sh scripts/test_playlist_preparation.sh` で実行できます。

開始・音源準備完了の応答が通信切断（`NSURLErrorDomain -1005` など）で失われた場合は、ルームの最新状態で操作結果を確認します。成功済みならそのまま進み、未完了なら同じゲーム・ラウンドに限って1回再試行します。カウントダウンへ進んだ後に届く古い準備エラーは表示しません。応答消失・再試行・実際の通信障害の回帰テストは `sh scripts/test_room_action_recovery.sh` で実行できます。

## 先に Coolify サーバーを用意する

正解発表には「サビ位置の相違を報告する」ボタンがあります。スケールインする確認画面から匿名で送信すると、曲情報・実際に再生した処理（サビDB、Songle、プレビュー、曲長推定など）・開始位置が開発者の Discord に届きます。サーバー環境変数 `DISCORD_CHORUS_WEBHOOK_URL` の設定と再デプロイが必要です。[Discord通知の設定と報告内容](docs/chorus-reports.md)を参照してください。

ホーム画面の左上にあるメールアイコンから、意見・問い合わせを匿名で送信できます。入力は最大2,000文字で、サビ相違の報告と同じ確認ポップアップ・送信中表示・完了アニメーションを使います。送信先は専用の新しい Webhook です。サーバー環境変数 `DISCORD_FEEDBACK_WEBHOOK_URL` に設定して再デプロイしてください。この変更を含むアプリとサーバーの更新が必要です。匿名送信のため、個別の返信はできません。

複数端末の対戦と iTunes 試聴曲を使うサビトロにはサーバーが必要です。Apple Music のソロプレイとデモには不要です。対戦を使う場合は、この変更を含むサーバーを再デプロイしてください。

1. このリポジトリを Coolify が参照できる Git リポジトリにプッシュします。
2. Coolify の **New Resource → Dockerfile** でビルド基準ディレクトリを `server`、Dockerfile をその中の `Dockerfile` にします。公開ポートは `3000`、レプリカは **1** にします。
3. HTTPS ドメインを設定し、環境変数 `PUBLIC_BASE_URL=https://あなたのドメイン` と `DATA_DIR=/app/data` を設定します。`PUBLIC_BASE_URL` の末尾に `/` を付けません。
4. **永続ボリュームをコンテナ内 `/app/data` にマウント**します。マウント先を変えた場合は `DATA_DIR` も合わせます。永続ボリュームがないと再デプロイ時に履歴と進行中ルームを失います。
5. デプロイ後、`https://あなたのドメイン/health` が `{"ok":true}` を返すことを確認します。アプリをビルドする Mac のルート `.env` に同じ HTTPS URL を `APP_SERVER_URL` として指定します。

サーバーの設定例は `server/.env.example`、アプリの設定例はルートの `.env.example` を参照してください。アプリのビルドでは `.env` から `APP_SERVER_URL` を取り込みます。

## Apple Music の設定

MusicKit for Swift を使います。Apple Music API の秘密鍵や手動の Developer Token はアプリに不要です。MusicKit が App ID を使って Developer Token を自動生成します。[Apple の設定手順](https://developer.apple.com/documentation/musickit/using-automatic-token-generation-for-apple-music-api)を参照してください。

1. [Apple Developer の Certificates, Identifiers & Profiles](https://developer.apple.com/account/resources/identifiers/list) で、このアプリ用の **Explicit App ID** を作成するか既存の App ID を開き、**App Services → MusicKit** を有効にします。
2. Xcode の **Targets → IntoL → Signing & Capabilities** で自分の Team を選び、Bundle Identifier をその App ID と完全に一致させます。現在のリポジトリの値は `com.intro.IntoL` です。署名プロファイルを更新して実機にインストールします。
3. Apple Music を利用できる Apple Account で iPhone にサインインし、Apple Music の有効なサブスクリプションを用意します。IntoL の「アカウント」で外部連携の「Apple Music」行を押してライブラリへのアクセスを許可します。許可を拒否した場合は iPhone の設定から IntoL のメディアライブラリアクセスを変更します。
4. 「プレイ」→「ひとりで」→「イントロ」→「Apple Music」からプレイリストを選びます。対戦する場合は全員が Apple Music に接続し、ホストは「みんなで」→「イントロ」→「Apple Musicで作る」を選び、ルームの待機画面でプレイリストを選びます。対戦ではライブラリ曲を Apple Music カタログに対応付け、曲名のバージョン表記・アーティスト・曲長が一致しない候補は除外します。参加者の地域で再生できない曲があると、そのラウンドの準備が完了しません。

Apple Music のプレイリストはイントロクイズで利用できます。サビトロでは iTunes 試聴音源の検索か、Apple Music プレイリスト内の曲と試聴音源の照合を使います。Apple Music の正解発表では、導入済みのサーバーSQLiteを最優先で参照し、SQLiteの更新を次の再生へ反映します。通信失敗時・SQLite未導入時はCloudKit Public Databaseの手動サビDBを使います。600曲の確認済みデータを同梱し、CloudKitの最新データを15分間隔で取得・キャッシュします。登録済み曲はSongleへの問い合わせを省略し、既存のSongleの値やキャッシュよりDBを優先します。未登録の場合は従来のSongle→試聴音源→推定位置の順です。共有音源・デモも同じ優先順です。共有音源はサーバーで曲名とアーティスト、曲長が一致する iTunes の試聴音源を照合します。ソロプレイでは対戦サーバーの設定がなくてもDBとSongleを参照します。[サビDBの登録・更新手順](docs/manual-chorus-database.md)を参照してください。

## Xcode で起動・確認する

1. `cp .env.example .env` を実行し、対戦またはサビトロを使う場合は `APP_SERVER_URL` を記入します。値が空欄でもデモは動きます。`.env` は Git の管理対象外です。値を変えたらアプリを再ビルドしてください。
2. [IntoL.xcodeproj](IntoL.xcodeproj) を Xcode で開きます。
3. **Targets → IntoL → Signing & Capabilities** で自分の Team を選び、Bundle Identifierがご自身のApp IDと一致することを確認します。追加済みのiCloud capabilityに合わせて[CloudKitの設定](docs/cloudkit-setup.md)を行ってください。
4. iPhone 実機を選んで **Run**（⌘R）します。必要に応じて iPhone のデベロッパモードを有効化し、Mac を信頼します。シミュレータでもデモの画面と一部音源は確認できますが、Apple Music の実再生は実機で確認してください。
5. まず設定なしで「プレイ」→「ひとりで」→「イントロ」→「オリジナル音源」→「プレイ開始」→ PUSH → 4択 → 結果 → 復習を確認します。
   「ショートカット」アプリから「ひとりで練習」を実行すると、同じオリジナル音源のソロ練習を直接始められます。
6. サーバーを設定したら2台の iPhone で共有音源ルーム、Apple Music ルーム、サビトロを順に確認します。サビトロでは iTunes に一致しない曲を除外します。終了後は「アカウント」で記録の同期状態を確認します。
7. Wi-Fi を一時的に切って5分以内に戻し、同じルーム・得点・ライフに復帰することを確認します。ホストの退出と待機室の「ホストを譲る」も試せます。

署名なしの iPhone 向けビルド:

```sh
xcodebuild -project IntoL.xcodeproj -scheme IntoL -configuration Debug \
  -destination 'generic/platform=iOS' -derivedDataPath /tmp/IntoLDerived \
  CODE_SIGNING_ALLOWED=NO build
```

サーバーのテスト:

```sh
cd server
npm ci
npm test
npm run test:socket
```

Swiftのプロフィール同期・ゲーム復帰・通信再試行・出題準備・結果履歴の回帰テスト（Mac上で実行。iCloudの設定は不要）:

```sh
sh scripts/test_cloud_profile.sh
sh scripts/test_game_recovery.sh
sh scripts/test_room_action_recovery.sh
sh scripts/test_playlist_preparation.sh
sh scripts/test_room_code.sh
sh scripts/test_reveal_audio.sh
sh scripts/test_manual_chorus.sh
sh scripts/test_result_history.sh
sh scripts/test_artwork_cache.sh
```

対戦の統計は計上済みラウンドと一緒に保存し、アプリ再起動後の復帰でも重複して計上しません。平均PUSH時間にはサーバーが受け付けた本人のPUSH時刻を使用します。デモ曲の復習データは曲IDで保存し、各端末の同梱音源を再生時に解決します。ルームの参加期限が切れた場合は復帰情報を消してプロフィール同期を再開します。

ジャケット画像は復習・正解発表・結果履歴・プレイリストで共通の読み込み処理を使います。取得済み画像は端末のキャッシュ領域に最大64MB保存し、再起動後やオフラインでも再利用します。キャッシュがない既存の保存曲は表示時に取得します。破損データは取得し直し、通信失敗時は画面の再表示やアプリの復帰で再試行します。画像URLは引き続きプロフィールに保存し、画像キャッシュは端末ごとに作成します。

Debugの画面確認では `--ui-preview=review` と `--ui-artwork-url=<画像URL>` を指定できます。画像を表示した後、画像配信を止めてアプリを終了・再起動すると、復習の再読み込みを確認できます。同じ画像URLを `reveal`、`solo-result`、`playlist` に指定すれば各画面のキャッシュ再利用も確認できます。

プロフィールの初回登録は認証情報を送信前に端末へ保存し、応答が失われても同じ情報で再試行できます。この登録の再試行と新しいSKIP条件を利用するには、アプリと対戦サーバーの両方を更新してください。

ローカル起動は Node.js 22 以降で `cd server && node index.mjs` です。iPhone からアクセスする場合は HTTPS の Coolify 環境を使います。

この開発環境では iPhone 向けビルドとサーバーテストが成功しています。XcodeBuildMCP では iPhone 16 Pro (iOS 18.6) シミュレータでのビルド・起動と、デモの PUSH から正解発表まで確認できました。App Intent のビルドとショートカットのメタデータ生成も確認済みです。ただし、このシミュレータの「ショートカット」アプリでは追加したアクションを検索できず、ショートカットからの実行は未確認です。コマンドラインの `simctl` は CoreSimulator と Xcode のバージョン差により利用できません。

Apple Music の実再生、iTunes と Songle のライブ動作、複数 iPhone の同時再生は実機での確認が必要です。

追加した曲名は [Billboard JAPAN の年間 Hot 100](https://www.billboard-japan.com/charts/detail?a=hot100_year&year=2025) と [週次 Hot 100](https://www.billboard-japan.com/charts/detail?a=hot100) を基に [scripts/build_jpop_corpus.py](scripts/build_jpop_corpus.py) で生成しました。題名だけを収録し、順位・アーティスト情報・音源は含めません。

## 自作音源と Songle URL

非商用のローカル調査用として、既存600曲とSongleのサビ位置をGit管理外の非公開SQLite DBに保存できます。初回のサーバー・アプリ更新後は、SQLiteの変更を自動同期して正解発表に反映できます。DBファイルは公開せず、アプリへは曲ごとの開始位置を返します。[取得・移行・手動編集・導入手順](docs/private-chorus-database.md)を参照してください。

自作または利用権のある WAV を `server/public/audio/` に置き、[server/catalog.json](server/catalog.json) に `id`、`title`、`artist`、`audioFile`、`durationMS`、`genre` を追加して再デプロイします。任意で `artworkURL`、`trackURL`、Songle に登録済みの元動画 `songleURL` を設定できます。ファイル名は英数字・`_`・`-` と `.wav` を使用してください。サーバーは登録済み WAV だけを配信します。初期6曲と PUSH 音は [scripts/generate_demo_audio.py](scripts/generate_demo_audio.py) で再生成できます。

## 利用条件について

個人学習用でも外部サービスの利用条件は適用されます。Apple の [iTunes Search API 文書](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/index.html) には試聴音源の用途制限が記されています。外部サービスの接続可否と利用条件を確認した上で使用してください。デモと自作音源の経路は外部連携なしで使えます。
